After examining the actual source files you uploaded, I can be much more specific.

## What I Found

### GOOD NEWS

Your centralization work is **partially working already**.

In `generator-service.ts`, when a QR is generated, you are writing:

```ts
await db.set(["qrCodes", qrId], {
  content,
  contentType,
  ...
  templateKey,
  displayDestination,
  formValues,
});
```

So:

✅ `templateKey` is saved

✅ `displayDestination` is saved

✅ `formValues` is saved

✅ `contentType` is saved

into the master `qrCodes` record.

That means the generator is not the main problem anymore.

---

# The Real Problem

The problem is now in the **QR Detail rendering layer**.

I found:

```ts
features/qr-detail/hooks/useQrDetail.ts
```

which does:

```ts
const content =
  data.qrCode?.displayDestination || rawContent;

const contentType =
  data.qrCode?.contentType || data.offlineContentType;
```

This is correct.

But then:

```ts
features/qr-detail/components/ContentCard.tsx
```

contains lots of parsers:

```ts
parseWifi()
parseContact()
parseSms()
parseWhatsApp()
parseEmail()

```

## Critical Observation

I do NOT see evidence that the QR Detail UI is using:

```ts
templateKey
```

as the primary source.

Instead it appears to be doing:

```ts
contentType
→ parse content
→ guess type
```

which means:

```text
WiFi QR
↓
content = WIFI:S:Home...
↓
parser tries to detect
```

rather than:

```text
templateKey = wifi
↓
render WiFi template
```

# Verification Bug

I found this:

```ts
const isQrGuardVerified =
  data.ownerInfo?.isBranded === true ||
  (data.qrCode as any)?.isBranded === true;
```

Meaning:

Verification depends on:

```ts
isBranded === true
```

NOT:

```ts
verificationStatus
```

NOT:

```ts
verified
```

NOT:

```ts
trustScore
```

So if a generated QR exists but:

```ts
isBranded
```

never reaches:

```text
qrCodes/{qrId}
```

then QR Detail shows:

```text
Unverified
```

even if the QR was created by the owner.

# Architecture Error #1

You have:

```text
contentType
templateKey
qrType
```

all describing similar things.

Example:

```text
contentType = text
templateKey = wifi
qrType = individual
```

Which one should QR Detail trust?

Currently different screens seem to trust different fields.

That creates inconsistent behavior.

# Architecture Error #2

History, My QR, QR Detail and Scanner are not reading exactly the same model.

Ideally:

```ts
QrRecord
{
  id
  content
  contentType
  templateKey
  formValues
  displayDestination
  isBranded
  ownerId
  verificationStatus
}
```

should be the single source of truth.

### My conclusion

Your generator is already saving the template metadata correctly. The reason QR Detail still shows generic "Text" and "Unverified" behavior is likely that the detail page is still rendering from `contentType/content` heuristics rather than using the centralized `templateKey`, `formValues`, and branded verification data that are now being stored in `qrCodes`.
