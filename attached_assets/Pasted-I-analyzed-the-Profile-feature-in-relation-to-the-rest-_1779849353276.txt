# Biggest Risk #1

## Too Many Firestore Reads

I found patterns similar to:

```text
Profile
↓
Load User
↓
Load Stats
↓
Load Saved
↓
Load Followers
↓
Load Following
↓
Load Notifications
```

If these are separate queries:

```text
5 screen opens
↓
5 Firestore reads
```

Not ideal.

---

# Better

Load:

```text
Profile Summary Document
```

Example:

```json
{
  "name": "Binan",
  "avatar": "...",
  "followers": 45,
  "following": 12,
  "totalScans": 120,
  "saved": 32
}
```

One read.

# Final Verdict

The Profile page is currently in a good position. It is **cleaner than QR Details, smaller than Generator, and easier to maintain than History**. The main things I would watch are:

1. Reduce Firestore reads by using a profile summary document.
2. Avoid recalculating statistics on every open.
3. Keep avatar updates isolated.
4. Split settings into dedicated sections before the screen grows larger.
5. Continue reusing shared components instead of creating new profile-specific card variants.

Right now, the Profile page is not a major performance concern compared with QR Details, History, and the Generator module.
